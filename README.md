# 美國總經儀表板

每次數據出爐後自動完成歸因、修正追蹤與交叉檢查，把就業、通膨與聯準會措辭
合成一個政策情境，產出一整個可直接截圖使用的靜態網站。

**五個模組**

| 模組 | 回答的問題 | 資料來源 |
|---|---|---|
| 勞動市場 | 就業在增還是減？失業率為什麼變？前月數字被改了多少？ | BLS CES／CPS、DOL、JOLTS |
| 通膨 | 漲價是誰造成的？住房落後多少？離 2% 目標多遠？ | BLS CPI、BEA PCE、Cleveland／Atlanta Fed |
| 聯準會文本 | 這次聲明改了哪些字？措辭往鷹還是往鴿走？目前重心在通膨還是就業？ | federalreserve.gov 會後聲明 |
| 長端與債務 | 30 年期為什麼在這裡？政府與科技巨頭的發債壓力有多大？ | FRED（財政部、聯準會、BEA、ICE BofA）＋ SEC EDGAR（科技巨頭的 XBRL 財報與發債申報，自動擷取） |
| 情境合成 | 就業 × 通膨落在九宮格哪一格？聯準會目前重心在哪一邊？距離下一格多遠？ | 上述四者 |

前三個模組解釋的是**政策利率往哪走**；長端模組解釋的是**曲線的形狀**。
兩者由不同的力量驅動，所以情境頁刻意分開列，不合成單一分數——
合成會讓「降息但長端不降」這種最關鍵的組合消失。

結論一律翻譯成「利升息／利降息」，寫給投資人看，不用專有名詞。

## 快速開始

```bash
pip install -r requirements.txt

# 先看畫面長相（不連網，用示範資料）
python run.py --offline

# 正式執行
export FRED_API_KEY=你的key          # https://fredaccount.stlouisfed.org/apikeys
python run.py
```

輸出是 `output/` 底下的一整個靜態網站（首頁＋分頁＋存檔），每頁都是自足 HTML。
本機直接開 `output/index.html` 時分頁連結是絕對路徑，建議用 `python -m http.server -d output` 預覽。

加 `--json` 會同時輸出 `output/latest.json`，供 P2／P4 模組串接。

## 這一版做了什麼

| 模組 | 回答的問題 |
|---|---|
| **KPI 卡** | 非農、失業率、時薪、參與率的當期值與動能 |
| **修正追蹤** | 這次的數字有多少是被前兩月下修吃掉的？初值系統性偏誤有多大？ |
| **產業貢獻度分解** | 這次的增減是誰造成的？剔除醫療社福與政府後還剩多少？ |
| **失業率變動分解** | 失業率下降是因為找到工作，還是因為人退出勞動力？ |
| **失業缺口 u − u\*** | 目前的失業率水準本身算緊還是鬆？（分解看變化，這裡看水準）|
| **失業結構** | 這些人是被裁掉的，還是被景氣吸引回來找工作的？ |
| **每週失業金申請** | 兩次就業報告之間唯一會更新的訊號：裁員速度與再就業難度 |
| **Regime 紅綠燈** | 八個關鍵指標目前處在什麼狀態 |
| **自動判讀** | 確定性規則引擎的交叉檢查結果 |
| **綜合分數** | 各指標 z-score 加權合成，附逐項貢獻（可解釋） |

## 兩個容易誤解的地方

**① 修正有兩種口徑，不要混用**

- **相對上次發布** — BLS 新聞稿講的那個數字（2026 年 7 月報告是 −103K）
- **相對初值累計** — 完整修正史（同期為 −146K）

畫面上兩個都顯示，並各自標明口徑。長條圖裡的橘色是「初值（首次公布）」。

**② 失業率分解用的是家庭調查就業**

`u = 1 − E/L`，所以分解成：

```
Δu ≈ −ΔE/L  +  (E/L)·(ΔL/L)
      就業效果     勞動力效果
```

就業必須用 **CE16OV（家庭調查）**，不能用 PAYEMS（機構調查），否則分解無法閉合。

另外注意一個反直覺的地方：**勞動力萎縮會把失業率壓低，不是推高**。因為退出勞動力的人同時從分子（失業人數）與分母（勞動力）中消失，而分子減得更兇。這正是「壞的下降」的機制。

## 日常調整

**改門檻**：編輯 `config/indicators.yaml` 的 `regime_lights` 段落。

**加／減指標**：在對應的 group 加一段即可，不必改程式。要暫時關掉某個指標，設 `enabled: false`（不必刪掉，日後要用再打開）。

**加規則**：在 `src/analysis/rules.py` 寫一個函式加上 `@rule` 裝飾器就會自動納入。回傳 `Flag(key, severity, headline, detail, lean)` 或 `None`。

```python
@rule
def r_my_check(ctx: RuleContext) -> Flag | None:
    if 某個條件:
        return Flag("my_key", "watch", "一句話結論", "支撐數字", "dovish")
    return None
```

## 設計原則

**量化與判定走確定性規則，不交給模型。** 規則引擎的輸出每次跑都完全一致，所以時間序列可比、可畫圖、可回測。模型的角色留到 P4，只負責讀規則結果寫敘述。

**修正追蹤要保留版本。** 每次執行都把當下抓到的完整序列寫進 `snapshots` 表（append-only）。就算 ALFRED 某天不可用，從第二次執行起也能靠本地快照比對出修正。

**逐序列容錯。** FRED 偶爾改 series id，或某個序列暫時抓不到。單一序列失敗只會記錄並跳過，不會讓整份報告產不出來。勞動頁會在底部列出失敗序列；其餘分頁目前只記錄在 GitHub Actions 的執行紀錄裡。

**這是給投資人看的，不是給研究員看的。** 每個區塊在視線所及只留
「**數字 ＋ 一句對利率的意思**」；方法論、名詞定義、來源註腳一律下沉到
頁尾的摺疊區。它們必須存在——沒有方法論的儀表板是黑箱，機構讀者反而
不會信——但不該擋在閱讀動線上。`tools/audit_prose.py` 量的就是這件事：
打開一張卡之後讀到的文字裡，方法論佔多少，目標 20% 以下。

**每個人想看的那一塊不一樣，所以卡區可以收合。** 每一頁只有最上方的
結論卡與緊接的第一張內容卡預設展開，其餘卡區收合。看勞動的人不必每次
捲過行業分解，看行業分解的人也不必每次先讀完修正追蹤——手機上首屏長度
因此少了六成左右。

收合的標題列一定要帶一句結論（`<h2 data-sum="…">`）。只寫標題的收合卡
比不收合還糟：讀者得逐一點開才知道哪一張有事。摘要一律取那一區**已經
算出來的判定**，不另外造句——摘要跟內文各說各話，收合狀態反而會誤導。

轉換由 `site._collapse_sections()` 一次做掉，各分頁不必自己包 `<details>`：
五個分頁一共 42 個卡區，手動包會漏、也會把本來就很長的 f-string 再撐大
一圈。卡片結構固定（`<div class="card">` 緊接 `<h2 id=…>`、卡片不巢狀），
機械式轉換最省，而且不可能有哪一頁忘了改。行為由 `tests/test_sections.py` 釘住。

**首頁最上面是「結論卡 ＋ 整體情勢」兩段。** 結論卡回答「現在是什麼情境」，
總述回答「為什麼、各方向的細節是什麼」——讀者的下一個問題就是後者，
中間不該再隔著四張模組入口卡。

結論卡先前是 **711px（佔手機一屏的 84%）**，其中共識列就吃掉 358px：
三個色塊 ＋ 一句話 ＋ 長端色塊 ＋ 三行說明，只顯示十幾個字，
而且跟旁邊的定位列講同一件事（三個色塊在 390px 下折成 2+1，右下角空一整格，
版面稽核量到填充率只有 10–24%）。共識列回答的是「各模組同不同意」，
那本來就是總述的第一句——搬過去之後結論卡剩 **295px**，只留眉標、
情境名稱、一句話、定位列與出口。四個資料日期也從眉標移到頁尾
（頁面副標已經有更新時間，結論卡的第一行不該花在時間戳上）。

**整體情勢（`src/analysis/brief.py`）：約 150 字的一段散文，五件事固定順序**
——政策方向與共識度、就業、通膨、聯準會最近一次會議、財政與 AI 如何一起
推長端供給。三條規矩：

- **沒有任何一句是寫死的模板。** 每一段都從對應模組**已經算好的判定**取值，
  所以任何一個模組的資料一更新（月頻的就業與 CPI、會後的聲明、季頻的 SEC
  財報、每天的殖利率），這段話就跟著變。
- **不用模型生成敘述。** 量化與判定走確定性規則、每次執行結果一致，
  是這個專案的核心原則，總述也不例外——它是**組裝**不是**寫作**，
  分支條件全部看得到、測得到。
- **寧可少講一段，不硬湊。** 某個模組沒有資料時那一段直接不出現，
  硬填「資料不足」只是佔字數。

長度護欄量的是**中文字數**不是 `len()`：數字、百分號、PCE／GDP／AI 這些
拉丁字母會把 `len()` 灌水（同一段話 `len` 是 238、中文字只有 154）。
上下限 90–190 由 `tests/test_brief.py` 釘住——超過就代表某個分支寫得囉唆，
那會直接毀掉「一眼看完」這件事。

結尾固定收一句**重點句**（升降息的可能性、解鎖條件是什麼），材料全部來自
已算好的判定：九宮格的政策傾向、「情境轉換門檻」標成關鍵的那一條、
反對票的方向。畫面上拆成獨立一行加粗——掃視的人只讀這一行也帶得走東西。

**（選配）模型潤稿層（`src/analysis/polish.py`）。** 組裝版讀起來有模板感——
每句都是「數字＋結論」的並列。設計原則本來就寫著「模型的角色留到 P4，
只負責讀規則結果寫敘述」，這一層就是那個 P4：模型**只改寫措辭**，
所有數字、方向、結論由規則層決定。三道防護欄，任何一道失敗直接用組裝版：

1. **數字鎖定**——輸出裡的每個數字都必須出現在組裝版裡，一個新數字都不准有；
   重點句的「重點：」前綴也必須保留。機械檢查（`polish.validate()`），
   不是「相信模型不會亂寫」。比對的是**數值不是字串**：組裝版寫「+2.0 萬」、
   模型改寫成「+2 萬」是同一個數字，比字串會把它判成「原文沒有的數字：['2']」
   而整段退回——聽起來像模型亂編，其實只是省掉尾數的零。
   正規化成 float 之後「2」與「2.0」收斂成一個，「4.1」與「4.2」仍然是兩個，
   嚴格程度沒有放寬。
2. **事實沒變就不重新生成**——五段事實做雜湊存在 `state/brief.json`。
   非發布日不會出現「數字一樣、措辭天天漂」；API 呼叫降到每月幾次，
   費用以分計（預設 Haiku，`BRIEF_MODEL` 可覆寫）。
3. **失敗退回**——API 掛了、驗證沒過、沒設金鑰、離線模式，一律用組裝版。

啟用：repo 的 Secrets 加 `GEMINI_API_KEY`（Google AI Studio，有免費額度）
或 `ANTHROPIC_API_KEY`，兩把都設時優先用 Gemini。不設就永遠走組裝版，
什麼都不會壞。金鑰失效但事實沒變時沿用舊快取，畫面不會突然變粗糙。
防護欄由 `tests/test_polish.py` 釘住。

**模型被汰換時自己換一個。** Gemini 的模型會退場，而退場後打過去回的是
404「models/X is not found for API version v1beta」——那句話看起來像網址
寫錯，實際上是「這把金鑰沒有這個模型」。差別很重要：前者要改程式，
後者只要換個名字。所以收到 404 時會自己去問 `GET /v1beta/models`
拿這把金鑰**實際**可用的清單，挑一個重試，並把整份清單寫進執行紀錄——
下次想固定用哪一個，把名字抄進 `BRIEF_MODEL` 就好，不必去猜。

挑選規則是 flash → flash-lite → pro，同組內正式版優先於 preview、版本號大的
優先，並排除 embedding／image／tts／live 這些別種用途的模型。
順序的理由是**失敗方式**不是價格：這個任務有硬性格式要求（長度、不准新增
數字、結尾必須是「重點：」），做不到就被 `validate()` 擋下退回組裝版——
也就是使用者會看到的那個「沒有潤稿」的結果。分組要明寫不能用子字串比對，
`flash` 是 `flash-lite` 的子字串，照順序比對會把 lite 歸成 flash。

`thinkingConfig` 只對 `gemini-2.x` 送：這個欄位在後續世代改過形狀，
一律送過去會被擋成 400。沒送只是慢一點，不影響結果。

**排版記號機械清掉，不算失敗（`polish._sanitize()`）。** 星號、井號、清單
項目符號在中文總經散文裡沒有正當用途，出現就是模型的排版習慣——拿掉不會
改變任何一個字的意思，就像編輯把手稿上的底線畫掉。先前是「看到 `**` 就整段
退回」，結果模型只要把「重點」加粗，一整段合格的改寫就被丟掉。
清理與鎖定要分清楚：**排版**機械修正，**內容**（數字、方向、結論）
一字不差地鎖著。`validate()` 仍然保留同一條檢查當後備防線。

去記號時要換成空字串不能換成空格：`**重點**：` 換成空格會變成
`重點 ：`，反而觸發「重點句前綴不見」那條檢查。

**字數範圍由組裝版的實際長度算出來，不寫死。** 先前提示詞寫死「140 到
170」，但組裝版的實際長度會隨資料變（實測 179–180 字），而驗證的上限是 190。
等於一邊要求模型壓掉 20% 的字、一邊又用另一把尺去量——照做會偏短、
不照做會頂到上限，兩種都可能被擋，而且失敗原因完全不同。改成貼著實際長度
給範圍、兩端各留 10 字緩衝，讓「照著做」跟「通過驗證」變成同一件事。

**推理鏈一定要關掉，而且欄位名稱跨世代不同。** 推理用掉的 token **算在
`maxOutputTokens` 裡**：額度給太緊，推理模型會把它花光然後回一個
`finishReason: MAX_TOKENS` 的**空字串**——不是報錯，最難查。
2.x 用 `thinkingConfig.thinkingBudget: 0`，3.x 之後改成 `thinkingLevel:
"minimal"`；認不出版本（例如 `gemini-flash-latest` 這種別名）就兩個都不送，
改靠 `MAX_OUT = 4000` 的額度撐住。額度給寬不會多花錢——計費看實際用量。
真的送錯欄位而被退成 400 時，會自動不帶那個欄位再試一次。

回應解析也改成**分辨得出哪一種空**：沒有 candidate（提示詞被安全過濾擋下）
與有 candidate 但沒有文字（`finishReason` 是 MAX_TOKENS 或 SAFETY）
會印出不同的訊息，兩者的處置完全不同。

**被字數要求逼出來的「數出聲音」。** 實際收到過這種輸出：

    ，(77)核(78)心(79) PCE(82) 3.3%(86)、(87)三(88)月(89)化(91)…

模型為了滿足字數範圍，把字元位置一個一個標進正文。這一次觸發兩件事：
畫面上全是括號數字，而且那些數字**全部**被數字鎖定判成「原文沒有的數字」，
連退兩次、整段被丟掉。兩道修正：提示詞明講「不要逐字計數、不要標註字元
位置、不要有括號編號」，並把字數範圍講成寬鬆參考；`_sanitize()` 另外清掉
「括號裡只有數字、沒有單位」的註記——但要出現三個以上才動手，
因為真正的散文偶爾會有「（3 票）」這種寫法，那有單位、不是編號。

**`thinkingLevel` 在 v1beta 不存在。** 文件寫的是 `thinking_level`，實際送出去
回的是 `400 Unknown name "thinkingLevel" at 'generation_config'`。camelCase 與
snake_case 在 proto JSON 是等價的，所以這不是大小寫問題，是這個 API 版本
根本沒有這個欄位。既然關不掉，3.x 就一個欄位都不送，改用 `MAX_OUT` 給足
額度——那才是真正在防「回一個空字串」的那道保險。每次先送一個註定失敗的
400 只是白花一個來回。（400 自動不帶欄位重試的退路仍然留著當後備。）

**暫時性失敗要重試，永久性失敗不要。** 實際發生過：伺服器回
`503 Service Unavailable`，整段總述就退回組裝版——而那個錯跟我們送什麼
完全無關，過幾秒再送多半就成功。不重試等於讓一次幾秒的伺服器抖動決定
首頁那一段的樣子。現在 429／500／502／503／504 會退避重試三次
（429 照 `Retry-After` 等，但設 30 秒上限，伺服器偶爾會回幾百秒）。
400／401／403/404 **不重試**：再送幾次都是同樣的結果，只是白花額度，
而且 404 本來就該走「換一個模型」那條路而不是重送。
退避刻意短（3 秒、9 秒）——這是每天跑一次的排程，不值得為了一段選配的
敘述卡住整個 workflow；三次試完還是不行就用組裝版，明天再說。

**重點句不交給模型。** 這是兩種退回的共同根因。模型同時被要求「壓在字數
範圍內」與「保留重點句」，而這兩件事會互相排擠——實測到的順序是：
第一次交出 206 字（超出 190 的上限）→ 帶著「太長」的理由重試 → 第二次為了
縮短，直接把整句重點句刪掉 → 「重點句的前綴不見了」。兩次都不是模型寫壞，
是我給了兩個會打架的要求。

現在只把**事實段落**送給模型，重點句由規則層原封不動接回去。三個好處：
① 「重點：」前綴變成**結構上保證存在**，不再靠模型配合；
② 少一個互相排擠的限制，字數更容易達標；
③ 重點句是整段裡最由規則決定的一句（升降息傾向、解鎖條件、還差幾個
百分點全部來自九宮格與觸發條件），讓模型碰它只有下檔沒有上檔。

字數上限也跟著先扣掉重點句的長度（`_target_range` 的 `reserve`），
否則模型寫到剛好合格、接上重點句之後仍然會超出護欄。

**「有沒有亂寫」跟「有沒有寫完」是兩件事。** 三道防護欄查的全是前者，
所以一段被截斷的輸出可以一路通過：實際印上畫面的那一次是

    …對此 7/29 會議維持不變，有 3 票主張升息，下次會議

後面直接沒了。長度 146 字在護欄內、數字全部合法，三道都沒攔住。
根因是推理吃掉了 `maxOutputTokens`，Gemini 回一段半截的文字並把
`finishReason` 設成 `MAX_TOKENS`——而先前只檢查「文字是不是空的」。

兩道新檢查：`finishReason` 是 `MAX_TOKENS`／`LENGTH` 就當失敗；以及
`looks_truncated()`——結尾不是句號這類標點就視為沒寫完。後者是純文字
判斷，不依賴任何供應商的欄位，換一家也仍然成立。

配套的三件事：`MAX_OUT` 提到 8000；推理**一律**試著關掉（`thinkingBudget: 0`
是 v1beta 認得的欄位，400 會自動退回不帶欄位重送，所以試了不吃虧，
不試才有實害）；`MAX_CJK` 從 190 放寬到 260——先前上限跟組裝版的實際長度
（179）只差 11 字，等於逼模型在「六段事實都講完」與「不超過上限」之間
二選一，而它選了砍掉最後一段。護欄的用途是擋住失控，不是逼稿子變短。

**推理關不掉時，換一個預設就不推理的模型。** 完整的失敗鏈條長這樣：

    ① BRIEF_MODEL=gemini-flash-latest
    ② 送 thinkingBudget:0 → 400 INVALID_ARGUMENT（新世代不接受關閉推理）
    ③ 退回不帶欄位重送 → 推理吃光 8000 token → finishReason=MAX_TOKENS
    ④ 截斷檢查攔下 → 退回組裝版

加大額度沒有用——那只是讓它想更久。唯一有效的處置是換一個**預設不開推理**
的模型（lite 系列），整個輸出額度都拿來寫字。所以截斷用專屬的
`TruncatedError`，跟其他失敗分開：只有它會觸發「換 lite 重試」。

挑選時 lite 優先，而且**版本由舊到新**——舊世代能用 `thinkingBudget` 明確
關掉推理，新世代反而不行。沒有版本號的別名（`gemini-flash-lite-latest`）
排最後：別名指向的是最新的那一個，正是我們在避開的那一種。

**驗證沒過先帶著原因重試一次。** 實際發生過：換上的替代模型把「重點：」
前綴弄丟了。格式錯誤跟 API 掛掉不一樣——模型看得懂「你上次錯在哪」，
把被退回的原因附在輸入裡再講一次，通常就對了。只重試一次：兩次都做不到
就是這個模型做不到，繼續燒額度不會變出第三種結果。防護欄本身一個字都
沒鬆——重試的結果照樣過同一套 validate()，不合格照樣退組裝版。

**首頁也走同一套收合模型，並且是通往情境頁的入口。** 首頁先前是全站預設最長
的頁（390px 下 4026px），卻是唯一沒有收合的——整站的閱讀模型在入口那一頁
不成立。而且它 body 內通往情境頁的連結是 **0 條**（labor×2、inflation×2、
fomc×1、rates×1、scenario×0），只剩導覽列上那四個字；讀者剛看過同一段結論，
理性推論是「我已經看過了」，於是全站唯一寫著「該怎麼擺部位」的那張表沒有
人會走到。現在：三張卡收合（只留關鍵訊號展開）、模組入口移到結論卡正下方、
結論卡底部一條 deep link 到 `/scenario/#positioning`（`openTarget()` 會自動
展開那張收合卡）。首頁只給情境描述的**第一句**，完整那段留在情境頁；
情境頁則刪掉逐字抄自長端頁的分項拆解。跨頁重複率：情境頁 16% → 9.6%。

**狀態檔開始累積情境歷史。** `state/snapshot.json` 先前只留 current 與 previous，
每期覆蓋一次，所以全站永遠回答不了「這一格待了幾期」「上次換格是什麼時候」
——而首頁那句「情境**仍是**停滯性通膨」正好會讓讀者立刻問出來。現在每換一期
append 一列（不到 100 bytes，上限 400 列）。**去重鍵是資料期別不是執行時間**：
排程每天跑但資料一個月才出一到兩期，用執行時間的話一個月會塞三十列一樣的
東西，「待了幾期」會變成「待了幾天」——答案隨排程頻率改變而不是隨數據改變。
這段歷史沒有辦法事後回填，所以優先開始累積。

配套三件事：錨點跳轉會自動展開目標（否則點導覽過去是一片空白）、
頁面提供「展開全部／收合全部」（收合狀態下瀏覽器的 Ctrl+F 找不到內文，
這是必要的補償）、列印與存 PDF 前自動全部展開。

**兩條橫捲列都要有邊緣漸層，而且「回首頁」不能只靠選單。** 主選單在 360px 下
`scrollWidth` 是 526px，**32%（166px）在視窗外**，右邊硬切、沒有任何提示。
更糟的是「把目前這一頁捲進視野」原本是**置中**，於是在長端與情境頁上
`scrollLeft` 被推到 166–196——「總覽、勞動市場、通膨」全部滑到左邊看不見，
讀者想回首頁會以為沒有路。三個修法：拆成 `.snav`（背景與漸層）＋ `nav.site`
（橫捲）兩層並加兩側漸層、捲動改成**最小移動**而不是置中（166→42）、
以及把每頁的 `<h1>` 做成回首頁的連結（站名回首頁是通用慣例，成本一個 `<a>`）。

**結論卡的字必須大於任何單一數字——這條規則有兩個漏網的 class。**
`.v-main` 在 `@media(max-width:400px)` 會降到 26px，但 `.modcard .m-value`（27px）
與 `.dbox .dscore`（30px）沒有跟著降。結果只在 ≤400px（剛好是 iPhone 標準寬度）
破功：首頁最大的字變成四張模組卡的數字、FOMC 頁最大的字是「+6.00」——
一個 −8～+8 的內部刻度，比「本次會議：偏鷹」還大。另外 `.k-value`／`.sax-val`／
`.bk-val` 三者在手機上跟 `.v-main` 同為 26px，四種東西完全平手等於沒有層級，
一併降到 24px。

**收合摘要不能在詞中間斷行。** 中文預設可以在任意兩字之間換行，於是收合清單上
出現「利升⏎息」「長端承壓最⏎重」這種第二行只有一個字的斷法——而這一列的用途
就是**掃視**，掃視靠的是在一行內抓到完整詞組。兩道處理：CSS 用
`word-break:keep-all`（只在空白與標點斷，真的塞不下時由 `overflow-wrap` 放行），
以及 `_glue()` 把「數字 ＋ 單位」「標籤 ＋ 數字」之間的普通空白換成不斷行空白
（「已卡至少 64 ⏎ 個月」「時薪年增 ⏎ 3.2%」）。欄位之間的「　·　」照樣可以斷，
長摘要仍然換得了行。`tests/test_sections.py` 釘住後者。

**收合列上的標題不能比數值顯眼。** 通用的 `summary{color:var(--series-1)}` 被
`.sect>summary h2` 繼承，於是每一列是「藍色 17px 粗體的標籤（每期都一樣的字）
＋ 灰色 12.5px 的數值（本期新的東西）」——層級剛好反過來，而且藍色＝連結是既有
的心理模型，讀者會不確定點下去是展開還是換頁。標題改回一般文字色，
摘要從 `--muted` 提到 `--text-secondary`。

**觸控目標除了高度還要驗間距。** `audit_layout.py` 原本只檢查 `height >= 40px`
且全數通過，但兩個都 44px 高、只隔 1px 的目標一樣按不準。加上間距檢查後抓到：
`.f-more>summary` 用 `padding:13px 0;margin:-7px 0` 把觸控盒撐得比視覺盒大 7px，
於是兩個「看起來隔了 14px」的元素實際只差 **0.9px**——在勞動頁點最後一條訊號的
「依據」很容易變成收合掉整張卡；存檔頁的兩個月份連結只隔 **1.0px**。
負 margin 只能用在上下都沒有相鄰可點元素的地方（例如 `<h1>` 的連結），
`.f-more` 不符合。跨卡的配對不計入——卡片邊界是很強的視覺分隔，
而且那是「展開全部」之後才會貼在一起，不是讀者看到的預設狀態。

**頁內錨點導覽只在頁面真的變長時才出現。** 舊版是常駐的第二列 chip，
跟上方的分頁選單長得一模一樣（都是圓角 chip ＋ 淺灰底條），一個是換頁、
一個是換段，層級完全沒有表達出來——那才是它看起來突兀的原因，不是配色。
量測到的另外三件事：手機上把 1021px 的內容塞進 362px 的視窗、右邊硬切
且沒有任何提示（讀者只看得到前三項，並且會以為就只有三項）；sticky 佔掉
59px 卻沒有 active 高亮，「我在哪」那一半沒做；列的是全部 `<h2>`，
「名詞解釋」「判讀說明」這種翻到底自然會看到的附錄也佔一格。

更根本的是它跟收合設計互相重複：收合狀態下整頁只有 2,300–3,000px，
剩下那八九條帶結論的標題列**本身就是目錄**。錨點列真正有用的時機是
按下「展開全部」之後——頁面會漲到一萬多 px。

所以改成：預設 `height:0`，JS 在展開第三個卡區時才淡入，出現後不再收回
（導覽列忽隱忽現比一直在還煩）。樣式降級成純文字列以拉開與主選單的層級差，
兩側依實際捲動位置給漸層，並用 `scroll` 事件標出當前段落、
在手機上自動把高亮那項捲進視野。

兩個實作上的坑：

- **登場時的版面位移。** 導覽列排在內文上方，出現時整頁往下推一列高，
  讀者剛點開的那張卡會跳走。Chrome／Firefox 的 scroll anchoring 會自己補、
  Safari 不會，所以先看瀏覽器動了沒、沒動才自己 `scrollBy`。
  關鍵是**判斷用的 `scrollY` 必須在改 class 之前讀**——讀 `scrollY` 會強制
  reflow，而 reflow 正是瀏覽器補償的時機；改完才讀會讀到補過的值，
  於是判定成「瀏覽器沒動」又補一次，剛好跳兩倍。
- **兩側的漸層不能用 `mask`。** mask 會連元素的背景一起挖掉，
  底下的內文會從縫裡穿過去。所以拆成外框（`.anav`，負責背景、貼頂與
  漸層覆蓋層）與內層（`nav.anchors`，只負責橫捲）兩層。

**九宮格的兩條門檻改成錨在聯準會自己的預測。** 先前是寫死的 2.3／2.9，
程式碼與文件裡都沒有任何依據——而它們決定整張固定收益部位對照表
（跨過 2.9 那一刻，存續期間建議從「中性偏長」變成「縮短」）。
這是這個專案裡權重與依據落差最大的一組數字。

現在改成：

```
低 = FOMC 長期通膨目標（PCECTPIMDLR）＋ 0.25
高 = FOMC 對「明年」的核心 PCE 預測中位數（JCXFEMD）
```

**為什麼取「明年」而不是「今年」**：聯準會預測的是**它預期會發生什麼**，
不是**它能接受什麼**。2026 年 6 月的 SEP 把 2026 年核心 PCE 預測在
3.2–3.5%，而實際也在 3.3%——用「高於今年的預測」當門檻會判成「不高」，
但同一份聲明裡有三票主張升息，通膨顯然還是約束。**明年的預測才是收斂
軌道**：高於它＝還沒走上回到目標的路。

`+0.25` 這一項是判斷不是外部標準，所以要寫出來：「已經回到目標」不能卡在
2.00 這個點上，BEA 對核心 PCE 年增率的年度修正常在 ±0.1–0.2 個百分點。
另外設了 0.25 的最小帶寬，避免聯準會的預測收斂到 2.0 時兩條門檻交叉。
抓不到 SEP 時退回 2.30／2.90，並在畫面上標示「後備值、沒有外部依據」。

**就業軸同樣換成外部標準，三條依據都不是本站選的：**

```
水準  失業率 vs FOMC 對長期失業率的中央趨勢（UNRATECTLLR／UNRATECTHLR）
        高於上緣 → 弱　·　低於下緣 → 強　·　區間內 → 中
動能  Sahm 法則觸發（0.50）             → 直接判「弱」
      三月均非農 < 損益兩平就業增速      → 往「弱」推一格
```

為什麼用 FOMC 的而不是 CBO 的 NROU：九宮格問的是「聯準會會怎麼做」，
而聯準會照**它自己的**估計行動。而且這樣兩條軸都錨在同一份 SEP 上。
**帶寬也不用選**——直接用中央趨勢的寬度（2026-06 SEP 是 4.0–4.3%），
那是 FOMC 成員彼此意見的分歧程度。

**為什麼不能只看水準**：聯準會 2024 年 9 月降息 2 碼時失業率約 4.2%，
**低於**當時多數的自然失業率估計——降息的理由不是水準，是惡化的速度。
純水準規則會完全錯過那一段。所以加兩條同樣有外部依據的動能條件：
Sahm 法則的 0.50 出自原始論文；損益兩平是由人口成長 × 參與率 ×
機構／家庭調查比推導出來的，「低於它」在定義上就是「撐不住目前的失業率」，
不需要任何人拍板一個數字。

**動能只往「弱」推**：往「強」推需要對稱的證據，而就業轉強沒有對應的
公認規則——寧可不推，也不要自己發明一條。

拿不到 SEP 時才退回舊的綜合分數 ±0.45／旗標淨值 ±3（沒有外部依據），
用到時畫面上會標示。「情境轉換門檻」那張卡也跟著從「綜合分數還差 0.80」
改成「失業率還差 0.2 個百分點」——後者是可以拿去對新聞的東西。

**判定依據：結論常駐、算式收合。** 這一塊做過一次「有做但看不到」——
整段包在一個 `.f-more` 展開列裡（12.5px、`--muted` 灰、排在圖例之後），
跟旁邊的「◆＝會隨重心改變的三格」同字級同顏色同位置，掃過去只會被歸類成
註腳。使用者的回報是「情境合成還是沒寫為什麼就業弱、通膨高」——
**做了跟沒做一樣**。

現在改成九宮格正下方兩條常駐的列，一條軸一條：

```
就業  弱   失業率 4.1% 仍在充分就業區間，但三月均非農 +2.0 萬低於
           損益兩平 +4.3 萬，增速撐不住現有失業率            ▾
通膨  高   核心 PCE 3.0% 與三月年化 3.6% 加權後 3.27%，
           高於門檻 2.50%                                  ▾
```

分層的原則：**讀者要的答案（為什麼是弱／高）永遠看得到，只有要自己驗算的人
才需要展開**看權重、加總、門檻出處與方向 vs 水準的對照。就業排在通膨前面，
跟九宮格的列欄與全站「就業弱 × 通膨高」的講法一致。
`tests/test_sections.py` 釘住的是「結論有沒有露在外面」，不是「有沒有這段」。

**展開後是「這一格是怎麼判出來的」的完整算式。** 這解決的是一個看起來像 bug
的東西：讀者在通膨頁看到「通膨面：本期方向不明」，翻到情境頁看到「通膨高」，
直覺結論是網站在自打嘴巴。實際上兩者問的不是同一件事——

| | 模組頁最上方的結論 | 九宮格的軸 |
|---|---|---|
| 在問 | **方向**：這一期的新訊號把政策往哪推 | **水準**：離目標多遠／相對自身歷史的強弱 |
| 怎麼算 | 旗標的鷹鴿淨值，門檻 ±1 | 核心 PCE 加權水準／綜合 z-score |

「水準很高、但這個月的新訊號互相抵消」完全可能同時成立。所以說明區把
兩條軸的**輸入值、權重、加權結果、門檻與門檻的出處**逐項印出來讓讀者驗算，
並且**只在真的會被誤讀的組合上**（水準高而方向偏鴿或不明、水準低而方向偏鷹
或不明）加一段對照解釋——同向時不印，天天印只會被跳過。
兩個模組頁的結論也改口成「本期方向不明」並註明水準要看情境頁。

**九宮格的通膨軸只能用同一個指標的水準與動能。** 先前送進
`scenario.classify_inflation()` 的是 `0.6 × 核心 PCE 年增 + 0.4 × 核心 CPI 三月年化`
——一個 PCE、一個 CPI。核心 CPI 長期比核心 PCE 高 0.3–0.5 個百分點（住房權重
差一倍、醫療口徑不同），所以那個混合水準有約 **+0.15 個百分點的常數偏誤，
方向固定往鷹**。而這裡的門檻只差 0.6 個百分點（2.3 / 2.9），偏誤足以把通膨
從「中」推成「高」；配上就業「弱」，格子就從「轉向降息」跳成「停滯性通膨」，
整張固定收益部位表跟著換掉。現在兩項都取核心 PCE。

**失業率的月變動要過 0.2 個百分點才算數。** UNRATE 只公布到小數一位，
所以先前 `|Δu| > 0.02` 的判定門檻實際上等於「只要不是完全持平就下判定」。
BLS 自己的標準是 0.2 個百分點才在 90% 信賴水準下顯著（家庭調查約六萬戶，
就業月變動的標準誤約 ±30 萬人）。低於門檻時旗標從 alert 降成 info 並加註
但書——先前一個統計上不可分辨於零的 0.1 個百分點，會產出 alert 級、
鷹鴿淨值權重 2.0 的結論，兩條就能翻動九宮格的列。分解的近似誤差超過
0.03 個百分點時也會標出來，因為那張卡的版面在宣稱「兩項相加＝總變動」。

**政策利率區間改由 FRED 自動取得**（`DFEDTARL`／`DFEDTARU`），`config/fomc.yaml`
降級成後備值。它先前被描述成「只用於畫面顯示」，但實際上 FOMC 頁的
「市場定價 vs 聯準會」是拿 `2 年期殖利率 − 政策利率中值` 判定的，門檻只有
±0.15 個百分點——漏更新一次降息（25 個基點）會讓判定平移 0.25，
足以把「市場偏降息」翻成「偏向再緊縮」，而畫面上完全看不出來。
這是專案裡唯一一個「漏更新會默默給出反向結論」的手動項。退回後備值時
KPI 卡會直接寫出來。

**「本期變化」看的是變化的方向，不是訊號的異動流水帳。** 一條**已解除**的
鷹派訊號，代表鷹派壓力消失了——那是**鴿派**的變化。先前畫面上掛的是訊號
自己的方向，於是四條解除的鷹派訊號會顯示成四個「利升息」，而同一張卡的
標題同時說情境往降息移動，兩者互相矛盾而且矛盾的是那四個章。現在按
**變化的方向**分成「偏降息／偏升息」兩欄，上方給一句淨結論，新觸發／已解除
降級成 ＋／− 符號。

顏色只保留一組語意：**對利率的方向**。先前橘色同時代表「新觸發」與「利升息」、
藍色同時代表「已解除」與「利降息」，一列裡兩個顏色互相打架。數字變動也一樣——
`key_metrics` 的 `up_is` 記的是「這個指標往上代表偏鷹還是偏鴿」，因為兩者不一定
同向：損益兩平就業增速變高代表同樣的非農其實更弱，數字往上但方向偏鴿。

**對照的是每個模組自己的上一期發布，而且結果會留到下一次發布。**

先前是「這次的快照蓋掉上次的」，於是比較的視窗只有 24 小時：就業報告落地
當天卡片會亮，隔天快照被覆蓋成發布後的狀態，比較變成「今天 vs 昨天」＝
沒有變化，卡片就熄了。**讀者在發布後第三天打開網站，等於完全錯過那張卡。**
對一個每週看一次的儀表板來說這是最沒道理的行為——邊際資訊量最高的那張卡，
偏偏在新聞剛發生之後就消失。

而且三個模組的發布節奏不同（就業每月第一個週五、CPI 每月中、
FOMC 每 6–8 週），用一個共同的「上期」去套本來就對不齊：畫面上會出現
「7 月就業報告 · 6 月 CPI · 7/29 聲明」這種三個模組停在三個期別、
卻共用同一個基準的情況。

所以 `state/snapshot.json` 改成**每個模組各存 current 與 previous 兩版**，
以資料期別（`vintage`）為輪替條件：

- 期別變了 → 舊的 current 成為 previous
- 期別沒變（同一期重跑）→ 只更新 current，**previous 不動**。
  這樣「7 月就業報告帶來的變化」會一直留到 8 月報告出來為止。
- `released`（第一次看到這一期的日子）在同一期重跑時也**不能覆蓋**，
  否則「N 天前發布」永遠會顯示「今天發布」，那個標籤就廢了

畫面上每個模組標自己的基準（「就業 7 月（對照 6 月）」），並標出距今天數。
`--only` 局部重跑完全跳過比對與存檔，不會污染基準。
舊格式的狀態檔會被當成 previous 平滑升級，改版後第一次執行不會漏掉一期。
行為由 `tests/test_change_basis.py` 釘住。

**「抓得到但是舊的」要另外擋。** 逐序列容錯保護的是抓取失敗，但 FRED 停止更新某條序列時**不會報錯**——它照樣回一整串觀測值，只是最後一筆是三個月前的，頁面照樣產出、照樣寫著今天的日期。`src/analysis/freshness.py` 依頻率設容忍值（月頻 75 天、週頻 21 天、日頻 12 天，都已把發布時差算進去），超過就在每一頁頂端掛警告條。門檻刻意寬鬆：寧可漏報，也不要每個月月初都跳一次假警報。

## 部署到 Netlify

架構是 **GitHub Actions 產生頁面 → commit → Netlify 純託管**。
Netlify 不執行任何 build，理由有三：API key 只留在 GitHub secrets、
不必在 Netlify 裝 Python 依賴、每次產出留在 git 歷史裡自動累積成 vintage 檔案庫。

**步驟**

1. 建一個 GitHub repo，把這個專案推上去（`output/` 要一起推，`.gitignore` 已設好）
2. repo → Settings → Secrets and variables → Actions → New secret
   名稱 `FRED_API_KEY`，值填你的 key
3. Netlify → Add new site → Import from GitHub → 選這個 repo
   - Build command：**留空**
   - Publish directory：`output`
4. 完成。之後 GitHub Actions 依排程跑，push 後 Netlify 自動部署

**排程**（`.github/workflows/update.yml`）：`45 13 * * *`，每天一次。

不對準個別發布日，理由是執行本身是冪等的——非發布日跑起來只是重新產生同一份
頁面，沒有副作用。一份日排程就涵蓋就業報告、失業金、JOLTS、CPI、PCE 與 FOMC，
不必維護發布日對照表。

13:45 UTC 在美東夏令是 09:45、冬令是 08:45，兩者都在 08:30 ET 發布之後，
**所以換季不必手動調整**。也可以在 Actions 頁面手動觸發（workflow_dispatch）。

用量約每次 2–3 分鐘、每月不到 100 分鐘，私有 repo 免費額度為 2,000 分鐘／月。

**時鐘**（`src/clock.py`）：畫面上的時間與所有「今天」的算術一律走台北時間，
全站只有這一個來源。Actions 的 runner 時鐘是 UTC，兩件事會因此出錯：

1. **時間戳沒標時區。** 排程 13:45 UTC 跑完，畫面印「更新於 13:46」，
   但操作手冊寫的是「每天晚上 21:45 更新」——同一次執行兩個數字差 8 小時。
2. **日期整個差一天。** 台北比 UTC 早 8 小時，所以**台北的 00:00–08:00
   之間 UTC 還停在昨天**。這段時間 push 觸發重建，「N 天前發布」與
   「距下次發布還有 N 天」全部少一天。不會報錯，數字只是默默地錯，
   而且只在一天當中某八個小時裡錯——本機白天測永遠測不到。

`clock.py` 用**固定偏移 +8** 而不是 `zoneinfo("Asia/Taipei")`：台灣自 1979 年起
沒有夏令時間，UTC+8 是常數；`zoneinfo` 則要讀作業系統的 tzdata，
精簡容器裡常常沒有這包，缺了就是執行期爆炸。

`tests/test_clock.py` 除了驗證換算，還會**靜態掃描全庫**——任何檔案再出現
裸的 `datetime.now()` 或 `date.today()` 就直接失敗。這條比前面那些斷言重要：
真正會壞的不是 clock 自己，是日後有人在別的地方又開了第二個時鐘。

**搜尋引擎**：頁面帶 `noindex` meta，`netlify.toml` 另外送 `X-Robots-Tag` 標頭，
再加上 `robots.txt` 全站 disallow——三道都設了。但請注意這**不是存取控制**，
知道網址的人仍然看得到。日後若要真的擋，用 Cloudflare Access（免費 50 人）。

## 各模組的重點設計

**勞動**：修正追蹤分兩種口徑（相對上次發布＝BLS 新聞稿的數字；相對初值＝完整修正史）。
失業率分解用家庭調查就業（CE16OV），因為要跟失業率同一份調查才閉合。
行業長條只顯示增減前五名，外加「相對自身歷史異常」的行業。

失業率那一張卡回答三個不同層次的問題，刻意分開：
**分解**回答「這次的變化是誰造成的」（會計恆等式那一層）、
**u − u\***回答「這個水準本身算緊還是鬆」（u\* 用 CBO 的 NROU，
是季頻模型估計且會被回溯修正，所以只當方向參考、缺口 ±0.2 以內一律當中性）、
**失業結構**回答「這些人是怎麼變成失業的」（永久性失業增加＝需求端收縮，
重新進入／新進入增加＝人被景氣吸回來找工作，兩者的政策意涵相反）。

**每週失業金申請**是整個模組唯一的週頻資料。初領（四週平均，優先用 DOL 自己
發布的 IC4WSA）看裁員速度、續領看再就業難度、失業持續期間中位數是第三個角度。
三者可以背離：裁員沒增加但續領一直爬，是勞動市場轉弱最早出現的形態。
水準會隨勞動力規模漂移，所以另外標出它在近一年裡的百分位。

**通膨**：分項貢獻 ＝ 權重 × 變化率，跟勞動的產業貢獻是同一套引擎。
權重來自 BLS relative importance 表，**每年一月更新，必須同步校準**。
住房項標記為落後項，並另外算「剔除住房後」的通膨。

**核心服務的黏性**單獨一區，因為那是降息時間表卡最久的一塊。
主軸是**方向不是水準**——3.9% 而且在加速，比 4.1% 而且在減速更該擔心，
而純水準的門檻只會報後者。三個角度：

- **動能階梯**：12m / 6m / 3m 年化並排。短天期低於長天期＝在減速，
  這也是聯準會官員談這一塊時引用的形式。差距小於 0.3 個百分點一律當
  「卡在原地」，因為月度資料的雜訊就有這個量級。
- **卡了幾個月**：三月年化連續高於 2.5% 的月數——黏性最直接的量度。
  門檻不取 2%（目標值）是因為月度雜訊會讓它頻繁穿越、數字失去意義。
  數到抓取範圍的盡頭時顯示「至少 N 個月」，不能寫成剛好 N。
- **黏性 vs 彈性**（Atlanta Fed）：彈性項先反應、黏性項最後才動，
  兩者收斂這一輪通膨才算走完。彈性反過來高於黏性，通常代表新的價格衝擊
  正在進來，而不是舊的通膨還沒走完。

CPI 與 PCE 兩側並列（`CUSR0000SASLE` 與 `IA001260M`）。**聯準會的目標是
核心 PCE**，兩者的權重差很多——醫療在 PCE 裡權重大得多，因為它含雇主付的
部分——所以背離超過 0.5 個百分點時畫面會明講以 PCE 那一側為準。

黏性核心 CPI 刻意**不**放在「是全面在漲，還是少數項目？」那一區：
中位數與截尾平均問的是**廣度**（多少項目在漲），黏性問的是**慣性**
（價格多久調整一次）。一個經濟體可以廣度低但黏性高——那對聯準會更難處理，
混在同一區會被讀成「還好」。

**聯準會文本**：完整逐字稿依規定延後五年公布，所以分析的是會後聲明、
投票紀錄與記者會。

抓取範圍由 `config/fomc.yaml` 的 `fetch.start` 決定，預設 **2025-01-01**（13 次會議）。
行事曆頁其實列到 2021 年，但措辭分數跨主席不可比，硬把更早的點放進趨勢圖只是雜訊。
客觀訊號分數是事實、跨主席可比，要拉長改這個設定即可。

**記者會**依主題（通膨／就業／利率路徑／資產負債表）抽出逐字稿原句，
開場聲明優先——那是準備稿，比即席問答精確。另外列出「命中計分詞典」的句子，
讓措辭分數可以被回推。抽句與計分共用同一套重疊解析；畫面只列權重最高的
五句，所以會一併標出「這幾句佔總權重多少」，讀者才知道加總為什麼不等於分數。

**兩個分數刻意不合成**：
- 客觀訊號分數＝政策行動 + 反對票 + 聲明自述的風險方向（主要依據）
- 措辭分數＝聲明用語的詞典計分（輔助）

理由是 2026 年 7 月的教訓：Warsh 上任後刻意縮短聲明、移除前瞻指引，
純看措辭會誤判成轉鴿；但當次有三票主張升息，市場也確實讀成偏鷹。
**合成會掩蓋這個背離，而背離本身就是訊號。**

系統另外內建「溝通方式改變偵測」：當聲明字數驟降或追蹤詞組大量消失時，
會在措辭分數旁標上「本次不可靠」，並明講此時要以客觀訊號分數為準。
分數本身仍然照常顯示（歷次表也保留該欄），因為連續性本身是資訊——
但頁面不會拿它去下任何結論，情境合成那一層也完全不讀這個分數。

**點陣圖已移除**。Warsh 任內縮減預測公布，這個輸入不再穩定存在；
留著會讓分數的可比性時有時無，不如拿掉並把權重放回政策行動與反對票。

系統另外輸出**反應函數**：委員會目前把雙重使命的哪一邊擺在前面
（通膨優先／就業優先／兩邊並重）。依據是聲明裡的風險制式句（±2）、
聲明對現況的描述（±1，「通膨仍高於目標」／「勞動市場已轉弱」）、
反對票的方向與張數（±1～2），以及記者會裡的明確表態（±1）——
記者會的權重刻意低一級，因為那是即席發言，而且逐字稿會後數日才發布、
不是每次都抓得到，給同等權重會讓判定隨「今天抓不抓得到 PDF」跳動。

四項的兩側刻意**對稱**，每一條加分項都有方向相反的對應項。
先前現況描述只有通膨側（+1）沒有就業側，而「通膨仍高於目標」這句
幾乎每份聲明都在，等於每次判定先往通膨側偏一分。

情境合成頁**每個體制各一張九宮格**，由這個判定選出適用的那張。
先前是一張固定格子加事後改寫，再用格名／修正後標題／徽章／部位落差說明
四個地方解釋那次改寫——實際上只改變九格裡的一格，工做得很少畫面卻很亂。
改成三張之後，格子裡寫什麼就是結論。九格中只有三格會隨體制改變
（中×高、弱×中、弱×高），其餘六格兩個使命同向或都不極端，
三張完全一樣；畫面上會標出來，讀者不必為那六格擔心重心翻轉。
行為由 `tests/test_scenario_regimes.py` 釘住。

**長端與債務**：主軸是「長端殖利率的供給壓力」。名目利率拆成實質利率、
通膨補償與期限溢酬三段，因為這三種上升的政策意涵完全不同——
只有期限溢酬那一段是聯準會降息也壓不下來的。

財政損益兩平用的是標準的債務動態式：

```
穩定債務比所需的基本盈餘 ≈ 債務比 × (有效利率 − 名目成長) ÷ (1 + 名目成長)
```

供給壓力分數**只由供給來源構成**（政府財政缺口、科技巨頭融資缺口、聯準會縮表）。
縮表算供給是因為：聯準會不再把到期的公債換新，那一部分就得由私人市場吸收，
對買盤而言跟「財政部多發同樣的量」是同一件事。
期限溢酬與 30 年減 10 年利差是被這些供給推高的**價格**，不是原因——
把它們加進同一個總分等於重複計算，所以改列成「壓力已經反映多少」的獨立指標；
投資級利差則定位為需求端的溫度計。兩者背離時（供給壓力大但價格還沒反映）
那個落差本身就是訊號。每一項的貢獻都列出來，不做成黑箱。

**季報之外另外追發債交易**。10-Q 是季末後約 45 天才申報，所以一筆新發債
最久要等 135 天才會進到季報數字裡。但發債本身當天就要申報，系統從
`data.sec.gov/submissions/` 抓近 120 天的申報來補這個時效缺口。

**只收真的有發行的文件**：

| 收 | 424B2／424B5 | 定價後的公開說明書補充，一份文件＝一筆發行 |
|---|---|---|
| 收 | 8-K 項目 2.03 | 「產生直接財務義務」，但**只在配不到 424B 時**才算獨立一筆 |
| 不收 | FWP | 行銷用的條款表。一筆債通常發兩到三份（初步、最終、定價補充），全收會讓一筆 125 億看起來像三筆 |
| 不收 | 424B3 | 多半是再售登記與生效後更新，公司沒有拿到新錢 |
| 不收 | 8-K 項目 1.01 | 8-K 最寬的萬用項：供應合約、合資、租約、循環額度修訂都走這一項 |

**預估版與定價版分開處理**。424B2／424B5 這兩個表格號**同時涵蓋兩者**，
光看表格號分不出來（實測過一份檔名寫著 `preliminary-prospectus-suppl.htm`
的文件，表格號就是 424B2）。分辨依據是 Rule 430B／430C 強制要求的封面法定用語：

```
The information in this preliminary prospectus supplement is not complete
and may be changed
Subject to Completion, Dated <日期>
```

定價版沒有這段。**預估版不計入筆數與金額**——它是同一筆的前身，兩三天後
就會有定價版，兩份都算等於數兩次。已經有對應定價版的預估版直接不列；
還沒有定價版的仍然列在明細裡標「尚未定價」，因為「有一筆正在路上」
對供給面本身就是資訊。

顯示的單位是**交易**不是申報。同一筆公開發行會產生三到四份申報
（預估版 424B、定價版 424B、8-K 2.03 四個營業日內，多幣別再加一份），
不合併的話畫面上同一筆債會出現三次、金額合計跟著翻倍——而那個合計是
這一段唯一有交易意涵的數字。

合併規則：同一家公司、日期相差十天以內視為同一筆，**不再要求金額相同**。
先前要求同金額，結果預估版（沒有金額）跟定價版（有金額）永遠配不起來，
兩份都被留下。合併後的金額是群組內**相異**金額的總和——多幣別分券要相加，
但同一個數字重複出現（重新申報、預估與定價金額一致）只能算一次。

金額從說明書封面解析，只認標準的分券寫法並加總：

```
$1,500,000,000  4.125% Notes due 2035
$2,000,000,000  4.875% Notes due 2055
```

沒有分券格式才退回明講 `aggregate principal amount` 的那個數字（兩者不相加，
封面常常兩種都寫）。**刻意不退回「封面上最大的數字」**——那個備案會抓到
貨架註冊額度（`up to $40,000,000,000 of debt securities`），而且錯得很有系統：
同一個額度在每份文件上都會再被讀成一筆新交易。實測災情是近 120 天合計
被灌到 1,828 億、等於季報申報值的 406%，而同期實際發行約 250 億。

解析不到就標「金額待確認」並附原文連結——**不用推估值填補，也不計入合計**。
一個錯的發債金額比沒有金額糟得多。

最後還有一道合理性檢查：合計超過最新一季季報申報值的 3 倍時，整個金額
**不顯示**，只留筆數與明細。這一段的價值在時效（比季報早三個月看到），
沒有金額仍然成立；但報一個錯了四倍的合計會直接毀掉整頁的可信度。

這些交易**刻意不計入供給壓力分數**：分數維持由經審核的 XBRL 數字決定，
否則同一筆發債下一季會被算第二次，歷史可比性也會斷掉。

submissions 端點的欄位名稱無法離線驗證，所以解析程式在欄位不符時會
回傳空並記錄失敗，該區塊直接不顯示。行為由 `tests/test_edgar_filings.py` 釘住。

submissions 的回應每家好幾 MB，而發債（424B／8-K 2.03）與財報新聞稿（8-K 2.02）
讀的是同一份，所以依 cik 在 client 上快取一次——抓兩遍除了把請求量與執行時間
乘二，兩次之間還可能拿到不一致的清單。

**科技巨頭改為自動擷取**。資料來自 SEC EDGAR 的 XBRL API——那是各公司
自己申報的原始標記，免費、無需金鑰、每季自動更新，且每筆都能回溯到具體的
10-Q 文件編號。`config/rates.yaml` 只需維護 `cik`（SEC 公司代號，不會變動）。

實作上有三個坑必須處理，都在 `src/sec.py` 裡：

1. **10-Q 現金流量表多半是「年初至今累計」而非單季**。直接取用會高估兩三倍。
   程式優先取本來就是單季的標記，沒有的話用同一會計年度相鄰兩筆累計值相減還原。
   累計序列的第一筆本身就是 89 天、看起來像單季，所以兩種來源必須**合併**
   而不是二選一，否則最新一季會停在很久以前。
2. **各家標記不同**。亞馬遜的資本支出標 `PaymentsToAcquireProductiveAssets`，
   其餘四家標 `PaymentsToAcquirePropertyPlantAndEquipment`。每個指標都備一組
   候選標記，**全部抓完再取資料最新的那一個**——不能拿第一個有資料的就走，
   否則亞馬遜會停在 2017 年那個早已停用的標記上。
3. **會計年度起點不同**（微軟 6 月底、甲骨文 5 月底、其餘曆年），
   所以「最新一季」對各家是不同期間，表格逐列標出期末日，不假裝是同一季。

**安靜地用了舊數字：一個空字串引起的災難。** 這一區曾經整整幾個月顯示的
都是 `config/rates.yaml` 的手動後備值，而不是 SEC 的即時申報——畫面上有
數字、比率算得出來、結論寫得斬釘截鐵，完全看不出異狀。根因是一行看起來
沒問題的程式：

    USER_AGENT = os.environ.get("SEC_USER_AGENT", "預設值")

workflow 寫的是 `SEC_USER_AGENT: ${{ vars.SEC_USER_AGENT }}`，而那個變數
沒設定時，GitHub Actions **不是**「不設環境變數」，是把它**設成空字串**。
`os.environ.get(key, default)` 只在 key 不存在時才回 default——key 存在而
值是空的，回的就是空字串。於是送出 `User-Agent: `（空的），SEC 直接擋掉，
五家公司全部抓取失敗，整區退回後備值。

三道修正：① 改用 `(os.environ.get(...) or "").strip() or DEFAULT`；
② 全部失敗時印 `log.error` 並把實際送出的 User-Agent 印出來；
③ 畫面分辨「部分退回」與「全部退回」——後者用最強的措辭直接說
「這一區的數字全部不是最新的，請先不要據以判斷」，並逐列標「未取自 SEC」。
`tests/test_hyperscaler_data.py` 除了釘住這一行，還**掃描全庫**禁止
`os.environ.get(鍵, 有內容的預設值)` 這種寫法再出現。

抓取失敗的公司會退回 config 的後備值，並在頁面上明確標示。
`ig_market.quarterly_issuance` 仍需每季手動更新（來源：SIFMA 季度投資級發行統計）。

關鍵比率是 `capex ÷ ocf`：超過 100% 代表自由現金流轉負，擴張必須靠舉債——
那正是這幾家從現金充裕的買方，變成投資級市場大型供給方的轉折點。

**兩個時效補丁與一個前瞻區塊。** XBRL 是這一區唯一的數字來源，但它只涵蓋
「已經花掉的上一季」，而且慢。三段各自補一塊：

| 區塊 | 補什麼 | 來源 | 進不進分數 |
|---|---|---|---|
| 資本支出指引 | 接下來一年**打算**花多少 | 手動維護（法說會） | 否 |
| 財報公布日 | 實績從季末後 40 天提前到約 3 週 | 8-K 項目 2.02 | 否 |
| 近期發債交易 | 發債從落後 45–135 天提前到當天 | 424B2／424B5（讀內容分類） | 否 |

三段都**刻意不進供給壓力分數**：分數維持由經審核的 XBRL 數字決定，
否則歷史可比性會斷掉，同一筆發債下一季還會被算第二次。

**前瞻指引為什麼手動**：這幾個數字不在任何申報欄位裡——它是法說會上用
自然語言講的（「approximately」「in the range of」），每家寫法不同、
每季還會改。硬解析的失敗方式是安靜地少一家或抓到錯的口徑，
而這一區的整個論點就靠這幾個數字。沒給指引的公司會單獨標示，
**不會被算成零併進合計**。

**表格號不是證券種類。** 這一段踩過的最貴的錯：程式只要看到 424B2／424B5
就當成發債。但那兩個表格號只代表「定價後的公開說明書補充」，賣的東西可能是
債券、普通股、特別股、存託股、結構型商品或 ATM 增發計畫。實際的災情是
Oracle 最高 200 億美元的**普通股 ATM 增發**、Alphabet 的 **Class A／Class C
股票發行**都被算成了債券，還進了合計金額。

現在改成讀文件內容分類（`sec.classify_security()`），方向刻意保守：
**只有拿到正面證據才算債券**（`aggregate principal amount`、`Senior Notes`、
`Notes due 20xx`），拿不準一律 unknown、不計入。漏掉一筆債的代價，
遠小於把一筆股票增發印成發債。排除清單走標題區而不是全文——債券說明書的
內文常常順帶提到普通股（「本公司普通股於那斯達克掛牌」），全文比對會把
真正的債券發行誤殺。

8-K 項目 2.03「產生直接財務義務」也**不算發債**：它涵蓋銀行貸款、定期貸款、
循環額度——Amazon 的 175 億美元 delayed draw term loan 就走這一項。
那是融資事件，不是公開債券發行，另外列、不進合計。

**分券金額會被加兩次。** 封面的分券表在「Calculation of Filing Fee」與摘要段落
各出現一次，舊程式把兩次都加進去：Meta 的 250 億變成 500 億、Amazon 的 250 億
變成 500 億。修法是依（幣別、金額、到期年、票息）去重——兩張真正不同的券
不可能四項全部相同，所以這個鍵不會誤併；同一張券在文件裡出現幾次都只算一次。

**幣別記號一起抓，不然加拿大幣會變成美元。** 舊的樣式只認 `$`，而
`C$1,250,000,000` 裡面就含有 `$1,250,000,000`——C$140 億直接被讀成 US$140 億。
現在幣別記號一起抓，而且 `C$`／`A$`／`US$` 必須排在 `$` 前面比對。
**解析階段保留原始幣別**，換算留到 `src/analysis/fx.py`：原幣是說明書封面上
白紙黑字的數字（歷史事實），美元是用 FRED 某一天的匯率換算的衍生值，
畫面上以原幣為主、美元為輔，並標出匯率與匯率日期讓人能重算。
FRED 的匯率序列方向不一致（`DEXUSEU` 是「一歐元換多少美元」、`DEXJPUS` 是
「一美元換多少日圓」），方向弄反不會報錯、只會讓數字錯上百倍，所以
`_DIRECT`／`_INVERSE` 分開列，並由 `tests/test_offering_classify.py` 釘住。

**筆數算的是交易，不是申報。** 分組鍵包含**幣別**：Alphabet 在同一週發過
€90 億與 C$85 億，那是兩筆不同的交易，合併成一個美元數字會讓兩筆都失真。
預估版與定價版只算一筆；沒有對應定價版的孤兒預估版列出但不計數。

**資料來源只有 SEC。** 畫面上明講這是「依 SEC filings 偵測之公開融資事件」，
不是「全球所有債券發行」——部分海外市場的當地發行不一定會產生可辨識的
SEC 申報。

**財報新聞稿為什麼只取日期**：新聞稿是非結構化文字，各家口徑
（是否含融資租賃、GAAP 或 non-GAAP）都不同，硬解會拿到一個不知道
是什麼的數字混進表格；兩週後 XBRL 就會給出經審核、標記明確的版本。
「這份新聞稿是不是講下一季」只比對兩個日期：申報日比該公司自己的
季末日晚 60 天以上就是下一季——一季約 91 天、新聞稿約季末後 20–30 天，
60 天落在兩群中間，兩邊都有 30 天以上的餘裕。用公司自己的季末日
而不是曆季，是因為微軟的會計季末在 6 月底、甲骨文在 5 月底。

**情境合成**：九宮格 ＝ 就業（強/中/弱）× 通膨（低/中/高），
而且**每個體制各一張**（就業優先／通膨優先／兩邊並重），由反應函數判定選出適用的那張。
單一固定對照表等於假設雙重使命的權重永遠一樣，但它會移動——
「就業弱 × 通膨中」在就業優先下是降息，在通膨優先下只是觀望。
格子裡寫什麼就是結論，不再事後改寫；三張之間只有三格不同。
觸發條件也會標出哪一軸才是目前的約束條件。

刻意不給機率——市場已有現成報價，有價值的是指出自己的判讀與市場定價的分歧。

長端供給壓力**不進九宮格**，另外列一段。理由同上：九宮格回答政策方向，
供給壓力回答曲線形狀。但兩者會交叉出一句話（例如「升息 × 供給壓力高
＝ 長端承壓最重」），並在部位對照表加上對應的但書。

## 已知限制

- **市場預期是手填的**。`config/consensus.yaml` 需要在每次數據公布前更新。
  沒填時系統會退回 AR(3) 時間序列外推值，並在畫面上標成
  「時間序列模型推估（非市場預期）」——它算得出意外值，但那是相對於
  歷史規律的意外，不是相對於市場共識的意外，兩者的交易意涵不同。
  連外推都算不出來（樣本太短）才會顯示「無預期資料」。
- **綜合分數的權重是暫定值**，尚未由歷史迴歸校準（哪個指標的意外真的移動了利率定價）。
- **擴散指數（diffusion index）未納入**，FRED 覆蓋不完整，需改走 BLS API。
- **CPI 權重每年一月要重新校準**，BLS relative importance 表更新後不同步會讓貢獻度失真。
- **市場隱含機率尚未接入**。規劃使用亞特蘭大聯準銀行的 Market Probability Tracker。
- **離線示範資料分兩類**。聯準會聲明與記者會逐字稿是 federalreserve.gov 的
  **真實原文**（2026 年 1、3、4、6、7 月共五次會議）；FRED 的時間序列則是
  程式生成的示範序列，統計特性接近真實但個別數值非實際發布值。

  要讓離線預覽也用真實序列，執行一次 `python run.py --save-fixtures`
  （需要 FRED key，通常在 GitHub Actions 上跑），它會把當次抓到的真實資料
  存成 `fixtures/*.json`；之後 `--offline` 會優先讀這些快照，
  頁面上的警示條也會跟著標明哪些模組是真實資料。
